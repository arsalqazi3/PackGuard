1. Project Abstract
Modern software development increasingly relies on AI coding assistants that generate installation commands and dependency recommendations. These assistants can hallucinate, producing package names that do not exist in any public registry. Attackers exploit this behaviour by registering malicious packages under these hallucinated names, an attack known as slopsquatting. Research by Spracklen et al. (USENIX Security 2025) found that package hallucination rates in code-generating large language models range from 5.2% to 21.7%, and a 2026 replication on newer frontier models found the threat persists even as rates compress. This project proposes PackGuard, a multi-layer software supply-chain defense platform designed specifically to detect and prevent this class of attack. PackGuard combines five connected layers: a Core Guard that verifies package names against real registries and flags suspicious naming patterns; an AI Risk Prediction layer that produces a calibrated risk score from package metadata and a cross-model consensus check, which flags package names that multiple independent AI models hallucinate identically; a Runtime Behavior Guard that executes uncertain packages inside an isolated sandbox and observes their actual behaviour; a Dependency and Provenance layer that records every package and every decision for later audit; and a Unified Decision Engine that converts all evidence into one action, allow, warn, quarantine, or block. The project builds on the MIT-licensed dataset released with the foundational USENIX study and on recent published research on Bayesian-calibrated hallucination detection, runtime behaviour mining, and supply-chain visibility. The expected contribution is a working, evaluated prototype that shows whether combining these layers of evidence improves detection over any single layer alone, together with measured precision, recall, and false-positive results on npm and PyPI packages.

2. Introduction
The research domain of this project is software supply-chain security, specifically the risk created by AI-assisted software development. As large language models become a standard part of the coding workflow, developers increasingly trust AI-generated installation commands without independently verifying that the suggested package actually exists. This trust creates a new and largely unaddressed attack surface.
This domain is important because open-source package registries such as PyPI and npm allow almost anyone to register a package name with no review process. When an AI model hallucinates a package name, an attacker who identifies that name early can register it before a legitimate developer does, embedding malicious code that is then installed and executed by any developer who trusts the AI's suggestion. Because AI coding assistants are now used by a large share of professional developers, even a low hallucination rate translates into a large number of exposed installation events.
The current situation is that this threat has only recently been characterised in the literature. Spracklen et al. (2025) provided the first large-scale measurement of the phenomenon, and later work by Churilov (2026) confirmed that although hallucination rates have fallen with newer frontier models, the threat has not disappeared, and a set of package names is hallucinated identically across multiple unrelated models. Existing commercial and open-source tools address general supply-chain risk but are not designed specifically around this AI-hallucination attack path, and no published tool checks whether multiple AI models independently hallucinate the same package name.
Computational and AI-driven research is directly relevant here because the attack itself originates from an AI system's behaviour, and because detecting it well requires combining several different kinds of evidence, registry status, package metadata, behavioural observation, and cross-model comparison, which are best combined using calibrated statistical and machine-learning methods rather than a single fixed rule.

3. Problem Statement
The problem this project addresses is not the absence of package-scanning software; several such tools already exist. The gap is methodological and applied: no existing system is designed specifically around the AI-hallucination attack path, and no published tool or study evaluates whether checking multiple AI models for shared hallucinated package names improves detection of this specific threat.
Existing detectors emit either a binary flag or a general-purpose risk score built from established malware and vulnerability signals; none combine a calibrated hallucination-specific score with post-installation behavioural evidence and cross-model consensus into a single, evaluated decision pipeline. This leaves an application gap: developers using AI coding assistants have no purpose-built defence against a documented, real-world attack pattern, and no empirical evidence yet exists on whether a multi-signal, AI-hallucination-focused approach outperforms simpler single-signal tools.

4. Motivation
The motivation behind this project is to develop a practical, evaluated defence against a documented and growing security risk introduced by AI-assisted coding. The project aims to:
Reduce the manual effort developers currently spend verifying whether an AI-suggested package is genuine.
Improve the reliability of AI-assisted development workflows without requiring developers to change how they work.
Automate the detection of hallucinated, suspicious, and behaviourally malicious packages before they reach a real project.
Provide a clear, explained risk decision for every package, rather than a black-box allow or block.
Improve on existing single-signal detection approaches by combining registry, metadata, behavioural, and cross-model evidence.
Maintain a centralised, auditable record of every dependency decision made on a project.
a. Aims and Objectives
The aim of this project is to design and develop PackGuard, an AI-assisted multi-layer software supply-chain defence platform that protects AI-assisted development workflows from package hallucination, slopsquatting, and related dependency risks.
The main objectives are:
Develop an installation-time guard that intercepts or evaluates package installation requests before a package enters a project.
Detect hallucinated, non-existent, suspicious, and typosquatted package names across the npm and PyPI registries.
Combine package metadata, registry status, and a cross-model hallucination signal into a single calibrated risk score.
Develop a machine-learning risk-prediction component and evaluate it against a rule-based baseline.
Develop a controlled runtime-analysis component that observes selected package behaviour in an isolated sandbox.
Construct a dependency and provenance record for security investigation and audit.
Create a unified decision engine that converts evidence from all layers into an allow, warn, quarantine, or block action.
Evaluate PackGuard against controlled benign, hallucinated, and malicious package scenarios, reporting precision, recall, and false-positive rate.
b. Scope of the Project
The scope of this project covers the npm and PyPI ecosystems, with the architecture designed to allow additional registries to be added later. The system will be integrated through a proxy-based or CLI installation workflow, with a CI/CD demonstration through GitHub Actions. Runtime analysis will be controlled and sandboxed rather than unrestricted, and will target packages flagged as uncertain by earlier layers rather than every package.
The project includes building a cross-model hallucination lookup table from a curated prompt set, training and evaluating a machine-learning risk model, constructing a dependency and audit record, and building a decision engine and a reporting dashboard. Full production-scale deployment, support for registries beyond npm and PyPI, and unrestricted execution of arbitrary untrusted code are outside the scope of this project.

5. Proposed Methodology
The project will follow a staged, layer-by-layer methodology, so that each layer produces a working, testable component before the next layer is built on top of it:
1. Requirement and threat modelling: define the threat scenarios, attacker goals, supported ecosystems, and the security decisions PackGuard must support.
2. Dataset preparation: use the MIT-licensed dataset released with Spracklen et al. (2025) as the primary source of confirmed hallucinated package names, supplemented by live PyPI and npm metadata and the OpenSSF malicious-packages database.
3. Core Guard development: implement registry verification, typosquat detection, and metadata analysis.
4. Cross-model consensus construction: run a curated prompt set through multiple large language models, extract suggested package names, and record names hallucinated by more than one model.
5. Risk scoring: implement a Bayesian-calibrated score combining the registry, metadata, and cross-model channels, following the two-channel design of Hillah et al. (2026).
6. Machine-learning model development: engineer features from package metadata and train and compare candidate models against the rule-based baseline.
7. Runtime analysis: build an isolated sandbox environment that executes flagged packages and records network, file, and process activity.
8. Decision engine integration: combine evidence from all layers into a single allow, warn, quarantine, or block decision.
9. Dependency and provenance recording: log every package, decision, and evidence trail for audit.
10. Evaluation: measure detection rate, false-positive rate, and risk-ranking quality against controlled benign, hallucinated, and malicious package sets, comparing the full multi-layer system against single-layer baselines.

6. System Architecture
The proposed system follows a layered architecture, consistent with the Layered Architecture pattern, with the following layers:
Presentation Layer
A web dashboard, built with Next.js, that displays risk scores, decisions, and dependency information, together with a command-line or proxy interface that developers interact with directly during package installation.
Application Layer
The Core Guard, Risk Engine (rule-based and machine-learning scoring, including the cross-model consensus check), Runtime Guard, and Decision Engine, each implemented as a Python service exposed through a REST API built with FastAPI.
Data Layer
A PostgreSQL database storing package records, risk scores, decisions, the cross-model hallucination table, and the audit trail.
Overall Workflow
Developer or AI coding assistant issues an install request → Installation-time interception point → Core Guard → Risk Engine (registry, metadata, and cross-model evidence combined into a calibrated score) → Decision Engine → Allow / Warn / Quarantine-to-Runtime-Guard / Block → Provenance Store → Dashboard.
