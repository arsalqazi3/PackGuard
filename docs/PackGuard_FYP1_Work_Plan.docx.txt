PackGuard: FYP-I Work Plan
Who does what, and when. For the team meeting on Monday 5 October 2026.
Team: Arslan Asad (DevOps lead), Ammar Hussain (AI/ML), M Asad Ur Rehman Bin Usman (Core Guard checks and evidence)
1. What we must deliver in the FYP-I final
Two layers, working end to end:
Core Guard (installation gateway): pip sends every package request through PackGuard first. PackGuard checks the package and either lets it through to PyPI or stops it.
AI Risk Prediction (a solid first version, not the full layer): a trained XGBoost model plus a hallucination evidence lookup, compared against a simple rule-based baseline.
In scope for FYP-I: gateway, existence check, typosquat check, metadata signals, hallucination evidence table, rule-based baseline, XGBoost model, simple allow/warn/block thresholds, saving decisions to Postgres, evaluation numbers.
Left for FYP-II: score calibration, live cross-model checks on every install, detailed explainability, Runtime Guard, Provenance, dashboard.
2. How we work in parallel
The idea is simple. We agree on a few fixed "contracts" in this meeting. After that, each person builds their own part against those contracts and uses fake data until the real parts are ready. Nobody waits for anyone else.
Arslan builds the gateway against a fake /evaluate that always says "allow".
Ammar trains the model on saved metadata files. He does not need the gateway.
Asad builds and tests the checks on a plain list of package names. He does not need the gateway either.
In weeks 6 and 7 we plug the real parts together.
3. Contracts to agree on in this meeting
3.1 API between the gateway and the checks
POST /evaluate
request:  {"name": "flask-jwt-helper", "version": null}
response: {"decision": "allow" | "warn" | "block",
           "score": 0.87,
           "reasons": ["not on PyPI", "found in AI hallucination list"],
           "signals": {"exists": false, "typosquat_of": null, ...}}

3.2 Feature list for the model (draft, to finalise)
Exists on PyPI (yes/no)
Package age in days, number of releases, days since last release
Number of maintainers, has a homepage/repo link, has a description
Download count (if available)
Name distance to the closest popular package (typosquat signal)
Found in the hallucination evidence table (yes/no, and how many models produced it)
Name patterns, for example length and common AI-style suffixes like -helper, -utils, -py
3.3 Database tables (Postgres)
packages: name, exists, metadata snapshot, last checked
evidence: name, source (Spracklen / Gemini / Groq), number of models that produced it
decisions: name, decision, score, reasons, time

Every decision is visible in the database

7. Team rules
Everyone works on their own branch and merges through a PR. CI must pass before merging.
Nobody changes a contract (API, features, tables) without telling the other two first.
Weekly check-in (15 minutes): what got merged, what is next, who is blocked.
If someone is blocked for more than 2 days, they say so in the group right away.
Held-out test set: the test names must not appear in the training data or in the evidence table. Otherwise the lookup simply "finds" the test names and our results look better than they really are. The jury can catch this.
Each person writes the report section for their own part.
