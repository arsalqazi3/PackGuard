High-level architecture

1. System architecture diagram

Four layers. The interception layer catches an install request before it reaches a real registry, the core layer scores it using registry, metadata and cross-model evidence, the decision engine turns that into one verdict, and persistence keeps a full record of what happened and why.

6. Class diagram

Core domain model. RiskScore and Decision are kept separate on purpose — a decision should always be traceable back to the exact score and evidence that produced it.

classDiagram
  direction TB

  class PackageRequest {
    +str name
    +str ecosystem
    +str requested_version
    +str source
    +datetime requested_at
  }

  class RegistryCheckResult {
    +bool exists
    +str nearest_neighbour
    +float levenshtein_distance
  }

  class MetadataSignal {
    +int age_days
    +int release_count
    +bool author_present
    +bool description_present
  }

  class CrossModelSignal {
    +bool in_hallucination_table
    +int model_agreement_count
    +str matched_models
  }

  class RiskScore {
    +float posterior_mean
    +float posterior_alpha
    +float posterior_beta
    +str epistemic_category
    +compute() float
  }

  class Decision {
    +Verdict verdict
    +str rationale
    +float risk_score
    +datetime decided_at
  }

  class SandboxResult {
    +bool executed
    +str network_calls
    +str file_writes
    +bool suspicious_behaviour
  }

  class ProvenanceRecord {
    +str record_id
    +str package_name
    +str decision_id
    +str evidence_hash
    +to_jsonl() str
  }

  class Verdict {
    <>
    ALLOW
    WARN
    QUARANTINE
    BLOCK
  }

  PackageRequest --> RegistryCheckResult
  PackageRequest --> MetadataSignal
  PackageRequest --> CrossModelSignal
  RegistryCheckResult --> RiskScore
  MetadataSignal --> RiskScore
  CrossModelSignal --> RiskScore
  RiskScore --> Decision
  Decision --> SandboxResult
  Decision --> ProvenanceRecord

8. Sequence diagram

One install request handled end to end. The Runtime Guard step only runs when the Decision Engine actually quarantines the package, most requests never reach it.

sequenceDiagram
  autonumber
  actor D as Developer / AI assistant
  participant P as Proxy (Verdaccio/devpi)
  participant C as Core Guard
  participant R as Risk Engine
  participant X as Cross-Model Table
  participant E as Decision Engine
  participant S as Runtime Guard
  participant V as Provenance Store

  D->>P: npm install / pip install
  P->>C: check(package_name)
  C->>C: registry probe + typosquat check
  C-->>P: verified name or registry-miss
  P->>R: score(package)
  R->>X: lookup(package_name)
  X-->>R: model_agreement_count
  R->>R: Bayesian + ML score
  R-->>E: risk score

  alt score is high risk
    E->>S: sandbox_test(package)
    S-->>E: behaviour report
  end

  E->>E: apply Allow/Warn/Quarantine/Block rule
  E->>V: log(decision, evidence)
  E-->>P: verdict + rationale
  P-->>D: install allowed / blocked / warned

11. State machine diagram

Lifecycle of a single package check, from the moment it is requested to the moment it is logged. Quarantine is the only state that can lead to more than one outcome.

stateDiagram-v2
  direction TB
  [*] --> Requested
  Requested --> CheckingRegistry : Core Guard invoked

  CheckingRegistry --> NameMissing : registry probe fails
  CheckingRegistry --> NameFound : registry probe succeeds

  NameMissing --> CheckingCrossModel : lookup hallucination table
  CheckingCrossModel --> Blocked : name in table (multi-model)
  CheckingCrossModel --> Blocked : name unresolved (single check)

  NameFound --> ScoringRisk : metadata + ML scoring
  ScoringRisk --> Allowed : low risk
  ScoringRisk --> Warned : medium risk
  ScoringRisk --> Quarantined : high risk

  Quarantined --> SandboxTesting : Runtime Guard invoked
  SandboxTesting --> Blocked : suspicious behaviour found
  SandboxTesting --> Allowed : cleared after test

  Allowed --> Logged
  Warned --> Logged
  Blocked --> Logged
  Logged --> [*]

  note right of Quarantined
    Only state that routes
    through the sandbox before
    a final verdict is reached
  end note
Build plan

12. Implementation structure

What gets built, in what order, and with which tools. Phases 3 and 6 don't depend on the phase before them, so they run in parallel with the main path rather than waiting their turn. The Decision Engine is deliberately last, it only makes sense once every other phase is producing real evidence to combine.
